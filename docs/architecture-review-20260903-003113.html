Problem

读取协议（transcript 在哪、怎么解析）本属各 provider 的实现细节，却被压进共享 service 的 if 链，随 provider 线性增长；services 反向 deep-import list/antigravity，seam 方向倒置。实证 bug：zcode 声明 supportsTokenUsage: true（provider-capabilities.service.ts:97），但读取链路没有 zcode 分支——zcode 同步器写死 jsonl_path: null（zcode-session-synchronizer.provider.ts:193-197），会话掉进 claude 兜底拼 ~/.claude/projects/…，必然 404。下一轮大概率又是一枚「+85 行 zcode 分支」提交。

Solution

给 provider interface 增加可选的 token 用量读取能力（挂 IProviderSessions 或独立 facet），每个 provider 自持读取协议；共享 service 收缩为「查 app session → 经 registry 分派 → 统一结果形状」，cursor 的「不支持」分支升级为协议化结果。

  • locality：zcode 404 这类 bug 不可能在分派层复发
  • leverage：新增 provider = 实现一个方法，不再改共享 service
  • capabilities 与实现不再各说各话
  • services→list 的反向 import 消失

Problem

它是全 provider 最有状态的单点，内聚崩坏且带三个真实缺陷：① 请求路径 sendRequest→startProcess 绕过熔断计数（:518），退避可被打穿；② shutdown 不取消已排期的重启 timer（:485-490），关服后仍可拉起新引擎进程，且 isShuttingDown 永不复位（:603）；③ 引擎崩溃重启后新进程不知道旧 session，无 re-subscribe、无 session-lost 通知，runtime 只能烧满 10 分钟超时。spawn 硬编码不可注入，测试被迫 cast 私有字段。

Solution

按生命周期拆三个 module：codec（纯函数）、engine supervisor（进程监管，spawn 注入、重启可取消、shutdown 可复位、熔断覆盖所有路径）、request router（服务端回调策略改为注入的 handler）。断连时的 session 语义显式化：要么 re-subscribe，要么通知 runtime 失败。

  • 三个缺陷变成可直测的单元
  • locality：进程生命周期问题集中一处
  • 产品语义（回调应答）离开传输层
